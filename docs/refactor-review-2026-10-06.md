### R01：收藏夹名称不是数据归属证明

**审查基线位置**：[收藏同步服务](../osu.Game.Rulesets.O2Lazer/Host/Persistence/Realm/O2JamSourceFolderCollectionService.cs)，原 `Synchronise()` 31–65 行及 `DeleteFeatureCollections()` 71–82 行；[设置会话](../osu.Game.Rulesets.O2Lazer/Host/Configuration/O2JamLibrarySettingsSession.cs) 34–51 行；[Realm 后端](../osu.Game.Rulesets.O2Lazer/Host/Persistence/Realm/O2JamRealmLibraryBackend.cs) 76–82 行。

同步时读取所有名称以 `O2Lazer: ` 开头的原生收藏，按名称匹配后替换其 Hash，不在计划中的同前缀收藏被删除；关闭功能时删除所有同前缀收藏。设置会话初始化会排队同步设置，默认关闭也进入删除路径。因此用户手建 `O2Lazer: 我的收藏` 可被误认领，打开设置亦可能触发删除。无需收藏曾由此功能创建。这与 README“只删除此功能管理的收藏夹，不影响无关收藏夹”不一致。

**建议**：将持久化的原生收藏 ID 与本功能的管理关系作为归属证据；显示名只用于显示/匹配展示，不作为删除权限。优先复用现有宿主存储能力，不因一项功能复制收藏数据库。历史同前缀收藏采取保守迁移，不能重新把所有前缀相同者直接认领；创建与归属记录之间的中断恢复也要明确。初始化关闭时只清理已确认归属的数据。

**验收**：临时 Realm 中覆盖手建同前缀收藏、同显示名但非管理 ID、混入外部 Hash、用户改名、同步开关切换、首次打开设置和中断恢复。非管理收藏及其 Hash 完全保留；已管理收藏的更新/清理符合契约。真实用户数据库不用于破坏性复现。

**实施结果**：已改为原生 `RealmRulesetSetting` 保存管理 ID 与计划名称，归属及收藏在同一事务提交；按原生主键查找，不按名称/前缀认领。用户改名后保留显示名，管理 ID 跨服务重建和 Realm 重启保持。旧无记录收藏保留，可能出现同名新收藏；损坏或歧义记录停止操作。新增 13 项归属场景，整组 145 项迁移/恢复、113 项既有契约和 14 项 OJM 格式测试通过，合计 272；语义图仍零违规。详细契约见[文件夹收藏夹归属](library-persistence-contract.md#文件夹收藏夹的管理归属)。

### R02：延迟载荷缺少源文件一致性校验

**位置**：[OjmReader](../O2Jam.Formats/Ojm/OjmReader.cs)，`ReadLazy()` 22 行、载荷闭包 220/248/335 行、`readRange()` 534 行；[OjmArchiveCache](../osu.Game.Rulesets.O2Lazer/Integration/Formats/Ojm/OjmArchiveCache.cs) 43–82 行及 `FileSnapshot`。

`ReadLazy()` 建立偏移/长度/解密状态索引后关闭文件。第一次读取 Data 时重新打开路径，但不核对是否仍是被索引的文件。外层缓存的长度/修改时间检查发生在取得缓存时，不能保护已经发给消费者的延迟载荷。

隔离复现：先索引 PCM `[1,2,3,4]`，随后将同一路径改为 `[9,8,7,6]`，旧 archive 的 Data 返回新 PCM。更复杂的替换还可能造成错误解密、长度错误或载荷异常。已经读取的数据与尚未读取的数据可能来自不同版本。

**建议**：在建立索引和延迟读取时携带明确的源身份，避免旧索引静默读取新文件。首次载荷读取前后检查文件快照只是候选方案，尚未证明满足用户的预览性能要求，不直接作为实施方案。优先评估能否结合现有打开/读取操作完成一致性判断，减少额外路径查询；持有读取句柄则需另评估缓存释放、文件替换限制及跨平台语义，不能直接引入。检测到变化后转入受控失效/重新加载；同长度、同时间戳修改仍按现有手动刷新边界说明，不能每个采样重新计算全文件 Hash。

**验收**：索引后替换、截短、修改、删除；已加载与未加载载荷不会静默混用。失效及 Lazy 异常后的刷新可恢复；OMC 解密状态、M30/OJM 载荷和缓存释放保持正确。

**预览影响边界（方案约束，未实施）**：用户现已明确，预览、ruleset 切换等没有明显加载状态的流程“绝对不能增加目前的加载时间”，这是 R02 的合入条件，包含选歌到首音等待及播放中空白。继续使用完整归档索引、跨难度缓存和 `Lazy<byte[]>` 首次载荷缓存，不在 `UpdateState`、readiness 轮询或每次采样播放中增加文件检查。原候选方案会在每个首次载荷读取前后增加文件属性校验，成本随新载荷数量增长，已加载载荷复用不增加此项成本；查询次数不等于物理磁盘读取次数，也不能换算为固定毫秒数或百分比。预览启动仍需等待到期音源，故后台检查也可能增加冷启动等待；没有实测数据，不能保证性能变化为零，慢盘/网络路径需单独评估。R02 保持未实施，不以“后台执行”或“平均开销小”作为满足此要求的证据。游玩入口允许少量等待不能放宽同一载荷读取器的预览调用路径。

保留十秒预取、有界并发/紧急优先、512 KiB 自动音流式分流、同曲兼容难度保留 BGM 与时钟、暂停/跳转/变速、预览跳过空前奏及缺失零号采样的处理。文件未变化时不重建播放轨道。索引后文件实际变化时，只拒绝旧索引继续读新内容，按既有失效/下次选择或显式刷新边界重建，不能为了检测每帧热切换或重启背景声道；同长度同修改时间变化仍不声称有强内容一致性保证。

实施验收除现有预览生命周期测试外，还应以读取/检查次数确认缓存命中和重复播放不触发新增文件查询，覆盖冷加载、预热复用、跨难度切换、快速换歌/取消和 seek。性能验收需与当前实现对照，观察选歌至实际首音、跳转后的恢复等待，以及播放中新增的非谱面空白；仅统计索引时间、时钟就绪日志或平均值不足以证明没有退化，还需关注较慢请求及新增断音。不能通过取消就绪等待、跳过应播放采样、扩大静音或整体预解码来满足指标。未证明满足要求前不合入 R02；本轮未执行 benchmark 或修改 R02 实现。

### R03：外部输入必须在分配大对象之前限制资源

**位置**：[回放档案](../osu.Game.Rulesets.O2Lazer/Host/Replays/O2JamReplayArchive.cs) 111–125 行；[回放持久化接入](../osu.Game.Rulesets.O2Lazer/Host/Persistence/Realm/O2JamReplayPersistencePatch.cs) 178 行的 `CopyTo()` 和 206 行的 `archive.Get()`；[OjnReader](../O2Jam.Formats/Ojn/OjnReader.cs) 56–93 行；[源快照](../osu.Game.Rulesets.O2Lazer/Host/Library/O2JamSourceSnapshot.cs) 24 行。

回放先执行 GZip 解压和 `ReadToEnd().Deserialize()`，随后才确认 ruleset/schema 和帧数据。没有压缩输入、解压输出、帧数量/字符串/数组总量的显式上限；全局导入器还会先解析其他 JSON/GZip 外壳。异常捕获不能保证内存、CPU 及解析前分配的上限。此处是源码确认的资源风险，未执行恶意大包或证明真实客户端已崩溃。

OJN Stream 读取、非 seek 流和源快照也可能整段 `CopyTo`；现有块数/测量数/采样数上限不等于字节总量上限。OJM 的大型完整歌曲载荷是合法用法，不能把 OJN/replay 的限制直接套给 OJM。

**建议**：先给回放输入、解压输出及结构项建立统一的有界读取/解析策略，达到上限在创建大型字符串/集合前失败；原始读取路径同样有界。随后为 OJN 快照和格式读取定义一致上限。阈值需兼顾真实长谱/长回放，集中定义并说明原因；保持正式 v5 格式及原生导入接缝，避免引入第二套格式协议。

**验收**：正常长回放可读；测试用小阈值验证压缩输入、解压量、帧/字符串数量超限立即拒绝，未知外壳不被认领，截断包失败且不写库。seek/non-seek OJN 的超限行为一致。测试无需消耗巨量内存或运行 benchmark。

**具体修改计划（供确认，尚未实施）**：分回放、OJN 两步实施，预算集中定义，并提供内部小阈值测试入口；不把限制暴露成新用户设置。

1. 回放持久化读取与外部导入均使用有界流读取。外部导入改用原生 `ArchiveReader.GetStream()`，避免 `archive.Get()` 增加整段 byte[] 读取副本；普通 `.osr` 的 `SingleFileArchiveReader` 返回文件流，可以在本功能分配前检查长度。不能泛化为所有 ArchiveReader 均不预分配：原生 ZIP 读取器会先物化条目，其入口边界单独说明。已有 byte[] 入口也先检查长度。已知长度在本功能分配前拒绝超限，未知长度按实际读取字节计数，不依赖 Length；恰好达到上限且 EOF 的输入应可读。
2. GZip 输入与解压输出分别限制绝对字节量，不仅检查压缩比。先得到有界 UTF-8 数据，使用原生 JSON token reader 做结构预检查，在创建业务 List/Dictionary 和长字符串之前限制深度、帧数、动作总量、暂停数组、字典项及 token 长度；未知字段和重复字段也计入预算，不能绕过。之后通过宿主 Newtonsoft 序列化设置流式反序列化，保留 snake_case、默认值及当前正式 v5 的字段语义，移除整体 `ReadToEnd()` 字符串副本。结构预检查不另建回放协议。
3. 初始候选上限为回放原始输入 64 MiB、解压 JSON 128 MiB、帧数 1,000,000、JSON 深度 32、单 token 原始 UTF-8 长度 64 KiB；动作/暂停/字典总量独立限制。动作列表的资源预算不擅自等同于“七键必定最多七项”，也不借此去重或改变录制内容。具体字段预算要与当前写入器往返验证；不设播放时长上限、不截断或丢弃尾部帧。自身创建/导出的回放也需满足读取预算，不能成功生成本项目无法读取的数据。
4. OJN 初始候选源文件上限 64 MiB，实际物化的 notes/BPM/measure-fraction 事件合计预算 1,000,000（每次解码累计，包括全难度读取）；现有 block/measure 上限继续生效。byte[]、全量流、非 seek 缓冲、加密复制/解密和源快照共用同一文件上限；计数检查在分配/追加集合前进行，不信任头部声明数量。源 Hash 扫描和导入提交 guard 同样检查打开流的大小，避免先扫描明显超限来源。
5. 可 seek 的未加密 `ReadChart()` 保留直接读取所选难度、跳过图片的路径，仅用已打开流做长度检查和解析计数；缓存命中不重读全文件，不增加 OJM 路径属性检查、Hash 或采样加载等待。OJM/OMC/M30 的完整歌曲音频不套用 OJN/replay 上限。保留元数据编码、可选图片容忍、原始引用 0/合法采样 ID 0、缺失采样和全部 -1 哨兵语义；R04 成绩范围校验及 R06 prefix 短读取仍独立处理。
6. 外部超限 O2Jam 输入在创建 ScoreInfo/写库前失败，不发布部分导入、不删除已保存成绩或原回放。导入接缝区分“未认领”“已认领但无效”“有效”，已确认属于 O2Jam 的超限/损坏输入不回落到 legacy 解码。其他 ruleset 或未标记外壳仍交给原来的导入流程；不能把 O2Jam 上限直接套到所有 .osr。对于无法在预算内确认归属的外壳，本功能停止解析并保持未认领，不声称能给其他导入器提供同样的资源保证。玩家本次完成的本地成绩区别于外部导入：如果自身回放达到预算，不能直接在 `prepareReplayArchive()` 抛异常而阻断原生成绩导入，应保留本局成绩、停止回放附件保存并明确反馈，不发布截断回放。

**原生对照（2026-10-06，只读参考源码）**：原生 `ScoreImporter.CreateModel()` 经 `GetStream()` 调用 `DatabasedLegacyScoreDecoder.Parse()`；解码器从 legacy 二进制头的 `UInt16` 读取初始统计和 MaxCombo，不能在这些头字段中表达负值，但 TotalScore 是有符号 `Int32`，lazer 附加 JSON 的统计又使用有符号字典值。解码后调用 `StandardisedScoreMigrationTools.UpdateToLatestScoring()`，准确率由统计和最大统计计算，`ComputeAccuracy()` 返回 `maxBaseScore == 0 ? 1 : baseScore / (double)maxBaseScore`，没有 `[0,1]` clamp；附加 JSON 的 Rank 会在重算后恢复。`ScoreImporter.Populate()` 校验谱面/ruleset 非空及 Mod 兼容并准备统计存储，没有本项建议的统一成绩范围检查；`ScoreInfo` 对 Accuracy/MaxCombo/TotalScore 的属性也不提供该验证。实时 `ScoreProcessor.Accuracy` 的 Bindable 范围不是导入上述计算方法的范围保障。

### R06：ReadChart 的前缀读取不满足通用 Stream 契约

**位置**：[OjnReader.ReadChart](../O2Jam.Formats/Ojn/OjnReader.cs) 85–90 行。

### 用户确认的性能边界（2026-10-06）

| 流程 | 用户确认的取舍 | 后续方案与验收要求 |
|---|---|---|
| 已有明确加载状态的流程，如选中谱面后进入游玩、进入回放 | 可接受少量加载时间增加 | 可在这些入口做必要的有界读取/解析；“少量”没有确认的毫秒数或百分比，不能扩大为任意延迟，也不能让同一检查进入其他调用路径后放宽要求 |

- **R02**：原首次载荷前后属性查询方案未证明符合预览约束，继续不实施；优先复用现有打开/读取及缓存信息。只在游玩加载阶段校验不能自动关闭仍存在于预览的延迟读取问题，长期句柄方案的文件替换行为也需另确认。

### 对 R02 的具体取舍

只在首次载荷检查，不等于只在首次选歌检查。一首曲目后段的新采样、seek 后的新音源、另一难度新用到的采样，均可能第一次触发 loader；相同采样的缓存复用没有该项新增检查。十秒预取可以提前完成工作，但预览起播本来要等待到期音源，因此后台执行不能证明首音没有延迟。正常无文件变更时不得增加 readiness 轮询/逐帧检查或重建已有音轨。

固定快照查询、结合现有打开句柄验证、长期持有句柄是不同方案，性能与行为结论不能混用。长期持有句柄可能改变用户能否在选歌期间覆盖 OJM；每个采样 Hash 整个 OJM 则会显著放大读取量，不作为候选。检测到替换后，是保留可用的已加载旧声音并要求重新选歌/刷新，还是让整个旧资源失效，需要明确恢复政策；不能静默切换编号或不断重启 BGM。源缺失/零号采样缺失不是源变化错误，继续保留物件、判定和队列推进。

### 对 R03 的具体取舍

回放预算、OJN 预算、本局成绩/回放附件的失败处理可以分别选择，不宜作为一个不可拆的修复批准。候选 64/128 MiB 和 100 万帧等是新的支持范围政策，不是格式标准；帧数不等于播放时长，不能将其解释为固定分钟数上限。32 层深度候选还需对齐宿主现有行为，不无依据收窄合法 v5。

现有 `E:\o2jam` 文件大小/头部统计为 OJN 文件预算留有余量，但不是完整解码或所有回放兼容证明。正常新解码的计数检查与整份回放的额外结构扫描不是同等成本；后者是较明确的加载 CPU 取舍。资源预算能让超限数据更早失败，减轻极端分配，却必然改变部分以前接受的数据的结果。反馈需要区分“超过支持预算”和“格式损坏”。ZIP 条目可能在原生 ArchiveReader 内已物化，本功能不能承诺阻止所有上游分配。

### 对 R07 和 R12 的具体取舍

R07 已有 100 条倒序撤销产生 5050 次 StateChanged 的计数证据，但没有毫秒数或客户端卡顿量测。通常尾部撤销可直接恢复必要状态，非严格逆序撤销不能照搬简单栈；已有结果快照在非尾部重算后可能过时，必须核对/更新。正确优化减少内部重算通知，但需保留真正的 Combo/Life/Pills/Jam/失败转换和正常命中动画，不能用丢掉全部通知换取速度。

R12 中的文件与 Realm 不共同原子提交是现有存储边界，目前靠文件预留、补偿及恢复处理，不等于已确认另有数据丢失缺陷。若以后选择加强提交协议，额外持久化/校验/刷写可能延长批次导入和启动恢复；当前没有这样的新实施方案，不能给出确定成本，也不能将它藏在 R10 结构拆分中。实机验收、修改补丁、升级宿主及改变存储协议是不同工作。

### 可分别确认的范围

- **额外工作范围较小、仍须按调用路径验收**：R04 的导入前校验、R05 的只读包装与有限数检查、R06 的 prefix 补读。尤其 R05/R06 进入选歌和导入准备，不能因为预计很小就豁免预览/写入不退化要求。
- **没有运行时变化**：R08 的测试/CI 与 R11 的文档；R12 仅补充验收时亦如此。
- **需要明确性能或支持范围取舍**：R02 的源一致性方案；R03 的回放/OJN 预算及本局超限保分；R07 的状态恢复方案。
- **维护收益优先、无需当作加载优化**：R09 的已确认内部冗余与 R10 的窄拆分；公开入口删除、宿主升级、存储提交协议另行界定。

## 建议的实施与确认边界

1. **第一批：数据保护和输入边界**。R01 收藏归属；R03 先回放后 OJN 总量；R04 成绩校验。先临时库/小阈值回归，保留现有持久化及回放身份。

3. **第三批：持续验证与清理**。R08 CI/音量矩阵/过滤器，R09 经核对的冗余，R11 文档。R10 只作实际修改所需的窄拆分；更大拆分另列清单，不为缩短文件引入新抽象。
