| 项目 | 两份客户端与当前项目的关系 |
|---|---|

## 七项对照及处理状态

C02–C05 已对齐；C01 使用用户选定的连续不对称区间，C06 按用户选定范围实现，C07 暂缓。编号沿用之前的 Remix 对照。

| 编号 | 两份韩服客户端 | 当前 O2Lazer | 实际影响 |
|---|---|---|---|
| C01 判定位置量化 | 输入位置向零截成整数 tick，再比较整数距离 | 连续区间 `[-6,7)`、`[-18,19)`、`[-25,26)` | 已按用户选择实现；普通整数 tick 目标边界一致，负位置/非整 tick 采用统一区间 |
| C02 LN 释放 BAD | 包含整数距离 25 tick | 连续 BAD 区间 `[-25,26)` | 同头判定，晚侧 +26 排除并超时 |
| C03 Jam 晋级 | COOL +2、GOOD +1，累计进度严格大于 `50×(Jam+1)` 才晋级 | 保留归一化 COOL +4 / GOOD +2，严格超过 100 后扣除 100 并保留余量 | 晋级时点与计分次序已对齐，连续 COOL 在第 26、51、76…击后晋级 |

### 边界与顺序的具体例子

对于整数端点 `T`、非负谱面位置，两份客户端的 COOL 区间为
`T-6 <= position < T+7`；当前项目显式采用同一区间，早期项目为 `T-6 <= position <= T+6`。在 BPM 150 时一 tick
约 8.33 ms。当前 Core 保留连续位置，直接定义早侧包含、晚侧排除的区间；lazer 时钟及 TimingMap
仍保持精确。负位置与非整 tick 目标采用统一区间，因此不宣称与原版截断算法全域等价。

从全新状态连续 26 个 COOL，两份客户端和修正后项目均得 5200，修正前项目为 5210。
严格累计阈值不表示
每一级都需要 26 个 COOL：持续连 COOL 时晋级在第 26、51、76…击之后，下一击才
使用新的加分。GOOD 混入时同样按累计进度比较。

普通 15 COOL 发药丸与 BAD 救回属于不同调用路径。救回在计分上仍是 COOL，
但这并不保证它在“连续 COOL 发药丸”或“长条允许继续”中等同于真实 COOL。
这两个区别应该由 Core 的明确状态转换表达，不能让 HUD 或 drawable 再判一次。

客户端 KS/BG 设置值为 255、音量 nibble 为 8 时，转换结果为 -15 dB，振幅约
0.178；项目为 50% 线性增益。pan 1/15 对应左右约 ±26.25 dB 的衰减参数，项目
映射到 Balance 两端。此处比较参数含义，没有测量设备输出。详细公式与 DirectSound
文档链接见 [C07 音频对照](remix-client-comparison.md#c07-谱面音量与声像)。

## 实际格式读取核对

对两包中的 OJN/OJM 数据，使用当前 `O2Jam.Formats` 和 `O2Jam.Core` 源码编译的
临时检查程序完成读取。检查程序运行于本地 .NET 10；没有改动正式项目的 net8.0
目标或依赖。文件数据从内存传入，不经安装器。每份 OJN 对照全难度与指定难度读取的
音符/BPM 序列，并检查头尾时间转换为有限值；每份音频库提取/解密样本并检查
RIFF/OggS 头部。结果记录在忽略的 `.artifacts/korean-client-corpus-check.json`。

| 项目 | O2JamO2 | Classic |
|---|---:|---:|
| OJN | 149 | 14 |
| 难度槽位 / 有可演奏节点的槽位 | 447 / 445 | 42 / 40 |
| 解码后的配对可玩 LN | 7,571 | 67 |
| 非单位小节长度记录 | 0 | 3 |
| OJM / OMC / M30 音频库合计 | 156 | 21 |
| 提取样本 | 36,443 | 2,458 |
| 读取异常 / 非 RIFF、OggS 样本头 | 0 / 0 | 0 / 0 |

O2JamO2 原始事件有 7,574 个可玩 LN 头，与解码后配对数量不是同一统计口径；
不能将原始头数直接作为最终长条数。现有格式模块会将未配对/重复头转为单点，
忽略没有头的释放，客户端在这些异常序列上的完整行为尚未逐项核对。

O2JamO2 有 148 份 `new` 封装；Classic 有 13 份，另各有一份普通教程。
Classic 版本字段为 13 份 2.9、一份 2.7；音频库为 13 M30、5 OMC、3 OJM。
它的 `o2ma769` 三个难度在第 21 小节有长度 0.75：客户端按
`round(fraction×192)` 得到 144 tick，项目按小节长度归一化，此值可以精确对应。
非整 tick 的小节长度仍可能因整数宽度与连续宽度产生差异，尚未覆盖。

两包实际网格均不超过 192 且能整除 192。客户端以整数 `192 / 槽数` 定位，并拒绝
超过 192 的块；项目允许更细及非整除网格。这是格式兼容范围差异，不能宣称这些
扩展输入在原客户端也会同样游玩。当前材料也没有完成懒读取文件路径、lazer 导入、
元数据编码观感、样本编号逐事件对应或音频后端播放验收。

2. **Formats / Integration / Host.Audio**：未来若启用 C07，应保留足够原始参数以翻译
