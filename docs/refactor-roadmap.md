## 使用方式

- **已完成**：本阶段限定范围已有实现和验证证据；不代表邻接模块也完成。
- **下一步**：接下来讨论并实施的阶段；未勾选项不视为已批准的具体方案。
- **待开展**：有方向，但仍需按组分确认设计后实施。
- **待决策**：依赖用户对产品行为的选择；不自行选定。
- 每项采用“现状 → 目标行为 → 原生可复用性 → 必要适配／补丁 → 实施 → 验收”的顺序。
- 阶段编号保持稳定；新增任务用子编号，不通过重新编号掩盖未完成工作。
- 完成时记录提交、测试命令／结果和未覆盖项。暂缓或取消应写原因，不打完成勾。
- 本路线图不预先规定所有类名、目录或程序集，也不等于授权一次性完成所有阶段。

## 不变的架构原则

1. 核心层拥有 O2Jam 时间语义、判定、长条状态、分数、Combo、Jam、药丸、生命和失败规则，
   不引用 lazer；原样用于另一个游戏是其独立性标准。
2. 衔接层分开处理格式解码与运行适配。解码输出数据，适配翻译输入、时间和结果，不复制玩法规则。
3. 宿主层优先复用 lazer 公开接口及合适的 Mania 实现，负责输入、时钟、对象生命周期、
   音频、回放、数据库、皮肤和显示。
4. 定制表现层读取数据和策略，处理等级、颜色、提示与交互；不能决定判定、分数或 PP 资格。
5. Mania Score 是并列玩法路线，采用原生 Mania 规则；O2Jam 核心不认识 Mania Score。
6. 补丁归属其服务的模块，安装、兼容检查和失败报告统一管理。
   不以补丁数量或是否依赖 Mania 判断架构好坏。
7. 公共设施须通过“新建 BMS ruleset 能原样使用”的检验；O2Jam 专用核心不强行通用化。
8. 背景音与 KeySound 不受全局效果音量影响。用户可见文本继续使用完整中英文资源。
9. 玩法状态、宿主结果提交、视觉消失分别管理；绘制不得反向决定判定。
10. 重点兼容旧成绩和 replay 的关联、读取与重现。旧导入数据布局不约束新结构；
    谱面元数据可以重建，但须先定义历史记录映射，不直接删除关联数据。

## R05 — 内核到 lazer 的接入

**前置：** R04；使用 R03 的运行对象与资源边界。

- [ ] 宿主输入和时钟转交给内核，明确输入选取和处理权，避免原生与核心各判定一次。
- [ ] 核心结果显式映射到原生 Judgement、ScoreProcessor、HealthProcessor 和成绩统计。
- [ ] 处理原生生命周期与 O2Jam 语义冲突，特别是 Combo、BAD、药丸与判定回退。
- [ ] Drawable 回调只组织适配，绘制读取长条状态；规则结算、宿主提交、视觉消失分开。
- [ ] 对象池回收和延后提交遵守宿主更新顺序，不把生命周期限制变成玩法规则。
- [ ] 核对暂停、恢复、重试、自动游玩与寻址后的输入／状态一致性。

**交付：** 运行桥梁、原生结果投影、状态驱动的 Drawable。

**验收：** 相同操作在独立内核与宿主中得到相同规则结果；判定只结算一次；
提前释放后允许继续显示，但不会继续保持或重复计分；对象回收不影响逻辑结果。
